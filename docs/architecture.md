# Tinyscript Architecture

Developer-focused internals guide. For language features and usage examples, see
the top-level `README.md`.

---

## 1. Project Overview

Tinyscript is a proof-of-concept JavaScript-like scripting language built on
[Eclipse Xtext](https://eclipse.dev/Xtext/). It demonstrates how Xtext can be
used to build a complete, executable language toolchain: grammar → parser → AST
→ interpreter, with IDE integration coming for free.

**Goals:**

- Educational exploration of language engineering with Xtext/EMF
- Sandboxed execution suitable for SaaS multi-tenant scenarios (user-submitted
  scripts run safely)
- Study of prototypal inheritance, closures, and dynamic typing in a minimal
  implementation

**Deployment modes:**

- **Eclipse IDE plugin** — syntax highlighting, auto-complete, validation in the
  Eclipse editor
- **Standalone REPL** — interactive command-line shell
- **Spring Boot web demo** — sandboxed script execution via REST API + browser
  playground
- **Embedded in Java** — `TinyscriptEngine` directly, optionally sandboxed with
  resource limits (as the REPL and the web demo do)
- **VS Code extension** — syntax highlighting (a TextMate grammar)

## 3. Execution Pipeline

```
Source text (.tys file or inline string)
  │
  ▼
Xtext parser
  (generated from Tinyscript.xtext via GenerateTinyscript.mwe2)
  │
  ▼
EMF AST (EObject tree)
  (model classes in src-gen/de/mkbauer/tinyscript/ts/)
  │
  ▼
TinyscriptValidator
  (static semantic checks: duplicates, constants, break / return / this
  in the right place, classes, imports, ...)
  │
  ▼
TinyscriptEngine                    ← main interpreter
  (tree-walking evaluator)
  │
  ▼
TSValue result
```

The parser and AST model classes are entirely generated — never edit the
`src-gen/` directory by hand. The validator and interpreter are hand-written.
Names are linked before a script runs: an unknown name is an error before any
statement executes (with a suggestion, see
`TinyscriptLinkingDiagnosticMessageProvider`). Syntax errors get messages in
plain words, with hints for Javascript habits
(`TinyscriptSyntaxErrorMessageProvider`).

## 4. Grammar & Parser (`Tinyscript.xtext`)

The Xtext grammar file is the single source of truth for the language syntax.
From it, Xtext generates:

- An ANTLR-based parser
- EMF model classes for every grammar rule (the AST node types)
- A language server (LSP) implementation
- Scope-resolution infrastructure hooks

**Key construct families in the grammar:**

| Family                  | Grammar rules                                                                                                                                                                                                                                                                                   |
| ----------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Top-level               | `Tinyscript` (imports, then `Global`), `ImportStatement`, `Statement`                                                                                                                                                                                                                           |
| Statements              | `VariableStatement`, `FunctionDeclaration`, `ClassDeclaration`, `ReturnStatement`, `IfStatement`, `ForStatement`, `WhileStatement`, `BreakStatement`, `ContinueStatement`, `ThrowStatement`, `TryStatement`, `AssertStatement`, `BlockStatement`, `ExpressionStatement`                         |
| Expression precedence   | `AssignmentExpression` → `ConditionalExpression` → `CoalesceExpression` → `OrExpression` → `AndExpression` → `BitOrExpression` → `BitXorExpression` → `BitAndExpression` → `EqualityExpression` → `CompareExpression` → `ShiftExpression` → `Addition` → `Multiplication` → `Unary` → `Primary` |
| Literals / initializers | `NumberLiteral`, `StringLiteral`, `BooleanLiteral`, `NullObject`, `UndefinedLiteral`, `ObjectInitializer`, `ArrayInitializer`, `FunctionExpression`, `ArrowFunctionDefinition`                                                                                                                  |
| Patterns                | `ArrayPattern`, `ObjectPattern` (in declarations, `for` loops and parameters)                                                                                                                                                                                                                   |
| Property/call chain     | `CallOrPropertyAccess` with `CallSuffix`, `DotPropertyAccessSuffix` and `ComputedPropertyAccessSuffix`                                                                                                                                                                                          |

Operators are enums in the AST (`BinaryOperator`, `UnaryOperator`,
`IncrementOperator`); `Operators` has helpers such as `baseOf` (the operator of
a compound assignment).

**Generated output location:** `de.mkbauer.tinyscript/src-gen/`

**Regenerating after grammar changes:**

```
Run: de.mkbauer.tinyscript/src/de/mkbauer/tinyscript/GenerateTinyscript.mwe2
(right-click → Run As → MWE2 Workflow in Eclipse, or via Maven)
```

## 5. Interpreter: `TinyscriptEngine`

**File:** `interpreter/TinyscriptEngine.java`

The interpreter is a classic tree-walking evaluator. It recursively visits EMF
AST nodes and computes a `TSValue` result for each.

### Dispatch

The single universal entry point is:

```java
public TSValue execute(EObject object)
```

It dispatches via an integer `switch` on the EMF classifier ID of the node,
which a `ClassValue` caches per implementation class (`NODE_KIND`):

```java
switch (NODE_KIND.get(object.getClass())) {
    case TsPackage.BINARY_EXPRESSION:
        return caseBinaryExpression((BinaryExpression) object);
    case TsPackage.BLOCK, TsPackage.ARROW_EXPRESSION_BODY:
        return caseBlock((Block) object);
    // ... one case per node type
    default:
        return defaultCase(object);   // TinyscriptUnsupportedOperationError
}
```

See §15 for why.

### Key State Fields

```java
private ExecutionContext         currentContext;       // active variable scope
private GlobalExecutionContext   globalContext;        // root scope (global object)
private Deque<ExecutionContext>  contextStack;         // scope stack (ArrayDeque)
private Map<Block, LexicalEnvironment> lexicalEnvironments; // hoisted declarations per block
private TSObject                 objectPrototype;      // Object.prototype singleton
private ResourceMonitor          resourceMonitor;      // enforces sandbox limits
private boolean                  sandboxed = true;     // refuses the native modules std:fs, std:io
protected int                    callDepth;            // current call stack depth
private OutputStream             stdOut;               // where print() writes
private StandardInput            stdIn;                // what std:io reads
private ModuleLoader             moduleLoader;         // null: import is an error
private volatile boolean         interruptRequested;   // set by interrupt() (Ctrl-C in the REPL)
```

### Context Stack Management

```java
enterNewExecutionContext(String name)
enterNewExecutionContext(String name, ExecutionContext outer)
leaveExecutionContext()
```

`enterNewExecutionContext` pushes `currentContext` onto `contextStack` and
creates a new child `ExecutionContext`. `leaveExecutionContext` pops it back.
This is called on every function call and for block-scoped constructs.

### Function Hoisting

Before executing a `Block`, `TinyscriptEngine` pre-scans it for its variables
and function declarations (via `getLexicalEnvironment(block)`, cached per
block). Function declarations are declared in the current context before any
statements run — matching JavaScript's function hoisting behavior. A block
without declarations of its own runs in the enclosing context; otherwise it gets
a new one.

### Exception-Based Control Flow

`return` statements throw a `TSReturnValue` (an unchecked exception wrapping a
`TSValue`). This unwinds the call stack back to `InterpretedFunction.apply()`,
which catches it and extracts the return value. `break` and `continue` throw the
singletons `TSBreak` / `TSContinue` (without a stack trace), caught by the
innermost loop. The validator ensures that they only occur where they can be
caught.

### Top-Level Entry

`caseTinyscript(Tinyscript object)` is the script entry point. It resets
`contextStack` and `callDepth`, sets up the global context, calls
`resourceMonitor.start()`, hoists top-level function declarations, then executes
all statements.

## 6. Type System: `TSValue` and `TSObject`

### `TSValue`

**File:** `interpreter/TSValue.java`

`TSValue` is a sealed interface; every runtime value is one of its
implementations:

| Tinyscript type                             | Java type                                                                   |
| ------------------------------------------- | --------------------------------------------------------------------------- |
| `undefined`                                 | `TSUndefined` (enum, single instance `TSValue.UNDEFINED`)                   |
| `null`                                      | `TSNull` (enum, single instance `TSValue.NULL`)                             |
| boolean                                     | `record TSBoolean(boolean value)`                                           |
| number (including `NaN`, `Infinity`)        | `record TSNumber(double value)` (`TSValue.NAN` for convenience)             |
| string (primitive)                          | `record TSString(String value)`                                             |
| object / array / function / `String` object | `TSObject` and its subclasses (`non-sealed`, implements `TSValue` directly) |

Values are created with `TSValue.of(double | boolean | String)`; objects are
values themselves, so there is no wrapper. Because the interface is sealed, a
`switch` over a `TSValue` is checked for exhaustiveness by the compiler (see
`asString()`, `asBoolean()`, `typeOf()`).

**Type checks:** prefer pattern matching (`value instanceof ArrayObject array`,
`value instanceof Function f`, `switch (value) { case TSNumber n -> … }`). The
remaining helpers cover cases with extra semantics: `isString()` (primitive or
`String` object), `isPrimitiveString()`, `isNumber()` (a number, but not `NaN`),
`isMathematicalInteger()`, `isBoolean()`, `isObject()`

**Conversion methods:** `asString()`, `asDouble()`, `asInt()`, `asBoolean()`,
`asObject()` (a cast; check with `instanceof TSObject` first), `typeOf()`

**Equality:** `tinyscriptEquals()` implements the language's `==` (no type
coercion, `null == undefined`, `NaN != NaN`); `equals()` / `hashCode()` are the
Java value contract of the records.

### `TSObject`

**File:** `interpreter/TSObject.java`

`TSObject` is the backing store for all objects, arrays, and functions.

```java
protected HashMap<String, TSPropertyDescriptor> properties;
private   TSObject proto;   // prototype chain pointer
```

The map keeps the insertion order, except that integer keys come first in
ascending order, as in Javascript. Each `TSPropertyDescriptor` carries:

- `TSValue value`
- `boolean configurable`, `writable`, `enumerable` (all default to `true`)

**Prototype chain lookup:**

```java
public TSValue get(String key) {
    TSPropertyDescriptor desc = properties.get(key);
    if (desc != null) return desc.getValue();
    if (proto != null) return proto.get(key);   // recursive walk
    return TSValue.UNDEFINED;
}
```

Writes (`put`) always go to the object's own `properties` map, never up the
prototype chain.

**Setting the prototype:**

```java
setPrototype(TSObject proto)
```

This stores the proto reference both in the `proto` field and as a regular
`"__proto__"` property, so prototype inspection works from script code.

**Static utility methods on `TSObject`:** `stringify(value)` (string conversion
for `print`, `+` with a string and `String(x)`), `toString(engine, value)` (the
items of `join()`), `toObject()` (the object for a property access; strings get
a wrapper), `toRelativeIndex()`.

**Display form:** `interpreter/Display.java` turns a value into the text `print`
shows (`{x: 1, s: "a"}`, `[1, 2]`, `Map {"k" => 1}`). Each object type overrides
`display(Display)` (not `toString()`, which is final and delegates to `Display`)
and formats the values it contains with `display.format(value)`. `Display` keeps
the path of objects being shown, so a cycle appears as `[Circular]`, and stops
at 50 levels of nesting (`[Object]` / `[Array]`). `stringify` uses
`new Display(true)`, which calls a user-defined `toString` (an
`InterpretedFunction`) at every level; `TSObject.toString()` uses
`new Display(false)` and never runs script code (REPL echo, error messages).
Strings inside values are string literals in double quotes, escaped exactly as
by Javascript's `JSON.stringify` (`TSString.quote`). The generated Javascript
has the same rules in its prelude (`__ts_display` / `__ts_str`, used by `print`,
by `+` with a string and by a wrapped `String`), so differential tests can
compare programs that print whole values.

**Memory estimation:** `estimateMemory()` returns `properties.size() * 8` bytes
(TSVALUE_SIZE = 8). Used by the resource monitor.

## 7. Scoping & Closures: `ExecutionContext`

### `ExecutionContext`

**File:** `interpreter/ExecutionContext.java`

Each function call and block creates a new `ExecutionContext` (an activation
record / stack frame):

```java
private HashMap<String, TSValue> values;   // variable bindings for this frame
private ExecutionContext          outer;    // parent scope (closure chain)
protected TSObject               thisRef;  // `this` value for this frame
protected boolean                functionContext; // true = function boundary
```

**Three core scope operations:**

| Operation | Method             | Behavior                                                                                    |
| --------- | ------------------ | ------------------------------------------------------------------------------------------- |
| Declare   | `create(id)`       | Writes `UNDEFINED` into local `values`; throws on duplicate                                 |
| Read      | `lookup(id)`       | Walks the `outer` chain; throws `TinyscriptReferenceError` if not found at global level     |
| Write     | `store(id, value)` | Writes into the frame where `id` was declared (walks chain); throws at global if undeclared |

`get(id)` is a local-only check (no chain walk) — used internally to avoid
infinite recursion.

### `GlobalExecutionContext`

**File:** `interpreter/GlobalExecutionContext.java`

The root scope, extends `ExecutionContext` with `outer = null`. All global
variables live as properties on a `TSObject globalObject`:

```java
private TSObject globalObject;
```

All scope operations delegate to `globalObject.get/put`. Unlike regular
`ExecutionContext.lookup()`, the global version does **not** throw on missing
identifiers — it returns `TSValue.UNDEFINED` (via `TSObject.get()`); unknown
names are already linking errors before the script runs. `this` outside a
function is `undefined`, as in Javascript's strict mode (and a compile-time
error), so the global object is not reachable from a script.

### Closures

Closures are implemented by `InterpretedFunction` capturing the
`ExecutionContext` that was active at function-definition time:

```java
private ExecutionContext outerContext;   // captured at definition time
```

When the function is called, `enterNewExecutionContext(name, outerContext)`
creates a new frame whose `outer` pointer is the **captured** context, not the
call-site context. This gives correct lexical scoping for closures.

**Arrow functions** additionally inherit `thisRef` from
`outerContext.getThisRef()` instead of from the call-site `self`, implementing
lexical `this`.

## 8. Function Types

```
TSObject
└── Function  (abstract)
    ├── InterpretedFunction  — user-defined; holds AST block + captured outerContext
    │   └── ClassObject      — a class: its constructor, callable only with new
    └── BuiltinFunction      — native Java lambda via BuiltinFunctionImplementation
        └── BuiltinConstructor — abstract; subclasses implement createObject()
              ├── ObjectConstructor, FunctionConstructor
              ├── ArrayConstructor, StringConstructor
              ├── MapConstructor, SetConstructor
              └── ErrorConstructor
```

All function types are `TSObject` subclasses, so functions are first-class
objects and can have properties set on them.

**`Function` (abstract base):**

```java
public abstract TSValue apply(TSObject self, TSValue[] args);
public abstract String getName();
public abstract int getLength();           // declared parameter count
public boolean hasInstance(TSValue value)  // implements instanceof via prototype chain walk
private boolean isArrowFunction;
```

**`InterpretedFunction.apply()` call flow:**

1. `resourceMonitor.checkMXCpuTimeAndMemory()` — CPU/memory check before
   entering
2. `engine.enterNewExecutionContext(name, outerContext)` — new frame, parent =
   captured closure scope
3. Increment `engine.callDepth`; `monitor.checkCallDepth()`
4. Set `currentContext.thisRef = self` (or `outerContext.thisRef` for arrow
   functions)
5. Set `currentContext.functionContext = true`
6. Bind the parameters (names or patterns; missing arguments are `undefined`);
   collect rest args into an `ArrayObject`
7. Hoist nested function declarations via `engine.getLexicalEnvironment(block)`
8. Execute `engine.caseBlock(block)`; catch `TSReturnValue` for explicit returns
9. `engine.leaveExecutionContext()` in `finally` — always restores previous
   scope

**`BuiltinFunction.apply()`:** Validates argument count, then calls
`implementation.apply(self, args)` where `implementation` is a
`@FunctionalInterface`.

**`BuiltinConstructor`:** Concrete subclasses implement `createObject()` to
allocate the new object. `apply()` returns `self` (the newly created object that
`new` passes in).

## 9. Built-in Runtime Library

Built-ins are registered in `TinyscriptEngine.initialize()` and also declared in
a synthetic `__builtins.tys` Xtext resource (so the IDE scope provider can
resolve them for auto-complete).

| Object       | Class                                                     | Key methods                                                                                                                                                       |
| ------------ | --------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `Array`      | `ArrayConstructor`, `ArrayObject`                         | `push`, `pop`, `splice`, `map`, `filter`, `reduce`, `sort`, `reverse`, `flat`, … (see the language reference), `Array.isArray()`                                  |
| `String`     | `StringConstructor`, `StringObject`                       | `charAt`, `indexOf`, `split`, `trim`, `replace`, `padStart`, … (see the language reference)                                                                       |
| `Number`     | `NumberFunctions`, `NumberObject`                         | `Number()`, `parseInt`, `parseFloat`, `isNaN`, `Number.isInteger`, `Number.isFinite`, `Number.MAX_SAFE_INTEGER`; `Number.prototype`: `toFixed`, `toString(radix)` |
| `Math`       | `MathObject`, `FreeBsdMath`                               | `PI`, `E`, `sqrt`, `pow`, `round`, `trunc`, `floor`, `ceil`, `exp`, `log`, `log2`, `sin`, … (`FreeBsdMath`: `log2` and `cbrt` as in V8)                           |
| `Map`, `Set` | `MapConstructor`, `SetConstructor` (`runtime/collection`) | as in Javascript; `keys()`, `values()`, `entries()` return arrays                                                                                                 |
| `Error`      | `ErrorConstructor`                                        | `new Error(message)`, `name`, `message`                                                                                                                           |
| `range`      | `RangeFunction`, `RangeObject`                            | `range(end)`, `range(start, end[, step])`: a lazy range of integers for the `for` loop; `length`, `toArray`, `map`, `forEach`, …                                  |
| `Object`     | `ObjectConstructor`                                       | `create`, `keys`, `values`, `entries`, `fromEntries`, `assign`, `getPrototypeOf`, `defineProperty`, `hasOwnProperty`, …                                           |
| `Function`   | `FunctionConstructor`                                     | `call`, `apply`, `toString`                                                                                                                                       |
| `System`     | `SystemObject`                                            | `currentTimeMillis`, `args` (the script's arguments)                                                                                                              |
| `print`      | `Print`                                                   | global function                                                                                                                                                   |

`Infinity` and `NaN` are plain global values. The `std:` modules add more (§13).
Each method is a `BuiltinFunction` whose `implementation` field is a Java
lambda; builtins check their argument types and count. Array and String
prototype methods are attached to the shared prototype object of their
constructor, so all instances inherit them via the prototype chain. A method
call on a primitive gets a short-lived wrapper: a `StringObject` for a string, a
`NumberObject` for a number; for numbers,
`TinyscriptEngine.toObjectForPropertyAccess` only allows the methods of
`Number.prototype` (any other property is a `TypeError`).

## 10. Sandboxing & Resource Monitoring

### `ResourceMonitor`

**File:** `interpreter/ResourceMonitor.java`

Tracks multiple resource dimensions and throws
`TinyscriptResourceLimitViolation` (unchecked) when a limit is exceeded.

**Tracked dimensions and when they are checked:**

| Event hook                              | Checked limit(s)                                                       |
| --------------------------------------- | ---------------------------------------------------------------------- |
| `recordStatement()`                     | `maxStatements`                                                        |
| `checkCallDepth(int depth)`             | `maxCallDepth`                                                         |
| `recordObjectCreation(TSObject)`        | `maxObjectCreations`, `maxObjectSize`, `maxObjects`, `maxMemory`       |
| `recordObjectSizeChange(TSObject)`      | `maxObjectSize`, `maxObjects`, `maxMemory`                             |
| `recordStringCreation(String)`          | `maxStringLength`, `maxObjects`, `maxMemory`                           |
| `checkObjectSize` / `checkStringLength` | `maxObjectSize` / `maxStringLength`, before an object or string grows  |
| `recordOutput(int)`                     | `maxOutputSize` (checked by `print` before writing)                    |
| `checkMXCpuTimeAndMemory()`             | `maxMXCpuTime` (thread CPU ns), `maxMxMAlloc` (thread allocated bytes) |

**Object tracking** (`enableObjectTracking()`): Uses a
`WeakHashMapWithCallBack<Object, Integer>` to track live `TSObject` and `String`
instances. When an object is GC'd, the callback decrements `totalMemory`
automatically. Memory is estimated as `properties.size() * 8` bytes per object
and `length * 2` bytes per string.

**MX Bean inspection** (`enableMXBeanInspection()`): Uses `ThreadMXBean` for
per-thread CPU time and `com.sun.management.ThreadMXBean` for per-thread
allocated bytes — both measured relative to thread start to isolate
per-execution costs.

### `ResourceLimits`

**File:** `interpreter/ResourceLimits.java`

Plain value object carrying all limit thresholds. Zero = unlimited.
`ResourceLimits.UNLIMITED` is a constant with all zeros.

```java
int  maxStatements;
int  maxCallDepth;
int  maxObjects;
long maxMemory;          // bytes
long maxMXCpuTime;       // nanoseconds
long maxMxMAlloc;        // bytes
int  maxObjectCreations;
int  maxObjectSize;      // max properties per single object
int  maxStringLength;
long maxOutputSize;      // characters written by print(...)
```

### Web Demo Limits

Set by `TinyscriptExecutionService`:

| Limit             | Value           |
| ----------------- | --------------- |
| `maxStatements`   | 5,000,000       |
| `maxCallDepth`    | 128             |
| `maxObjectSize`   | 100,000         |
| `maxMemory`       | 16 MB           |
| `maxStringLength` | 8 K characters  |
| `maxOutputSize`   | 64 K characters |

Without the output and string limits, a script that prints a large string in a
loop filled the heap (`OutOfMemoryError`) before any other limit applied: the
output buffer is not part of the tracked memory.

### Sandboxed Flag

`engine.sandboxed = true` disables privileged operations: the native modules
`std:fs` and `std:io` cannot be imported. The web demo always runs with
sandboxing on; the REPL runs with it off.

## 11. Validation & Scoping (Static Analysis)

### `TinyscriptValidator`

**File:** `validation/TinyscriptValidator.java`

Xtext calls `@Check`-annotated methods during parsing and on-save in the IDE.
Violations become error markers (red squiggles). The checks cover:

- declarations: duplicates in a block, unique parameter names, a `const` needs a
  value and cannot be assigned again, names starting with `__ts` are reserved
  (for the generated Javascript); a warning when a declaration hides a builtin
  (`for (const range : ranges)`);
- where statements may stand: `return` not at top level, `break` / `continue`
  only in loops, `this` only in functions, a constructor returns no value;
- targets and operands: what can be assigned or incremented, `delete` operands,
  `??` not mixed with `&&` / `||`, operands of `&&` / `||` that can never be
  conditions, patterns, shorthand properties;
- classes (only at top level, each method only once) and modules (`export` only
  at top level, imported names unique and read-only).

These checks are compile-time only — the interpreter does not re-run them at
runtime.

### `TinyscriptScopeProvider`

**File:** `scoping/TinyscriptScopeProvider.java`

Builds lexical scope chains for linking (an unknown name is an error before the
script runs), the IDE's cross-reference resolution and auto-complete. At run
time, the interpreter looks names up in its `ExecutionContext`s, not via the
Xtext scope provider.

## 12. Code Generator (Tinyscript → JavaScript)

**File:** `generator/TinyscriptGenerator.xtend` (compiled to
`xtend-gen/...TinyscriptGenerator.java`)

Transpiles the Tinyscript AST to modern JavaScript source text for node (it uses
`let`, classes, generators, `BigInt` and `globalThis`).

**Used by:**

- `/xcompile` REST endpoint (`TinyscriptCrossCompilingService`)
- the differential tests, which run the generated code with `node` and compare
  its output with the interpreter's

**Not used by the interpreter** — the interpreter walks the AST directly without
a JavaScript intermediate.

**Tested by:** `de.mkbauer.tinyscript.standalone.tests` — a plain-Maven module
(no OSGi) that verifies the generator differentially. See §16.

### Dispatch

The generator uses a long `instanceof` chain in the `generate(EObject)`
dispatcher (this is how Xtend compiles its dispatch methods). Unlike the
interpreter's integer switch, this is slightly slower but the generator is not
performance-critical.

### Runtime Shims (`generateBuiltins()`)

The generator prepends a prelude of JavaScript helpers so that the output
behaves like the interpreter and is self-contained: `__ts_add` (`+`), `__ts_eq`
(`==`), `__ts_bitwise` (53-bit bitwise operators via `BigInt`), `__ts_pattern`
(destructuring), `__ts_iterate` and the class `__ts_Range` (the `for` loop and
`range`), `__ts_display` / `__ts_str` (the text form), `__ts_throwable` /
`__ts_catchable` (`throw` / `catch`), and wrappers for `Map` / `Set`, `System`
and `print`. Some examples:

```javascript
// Tinyscript assert → JS function; its error is not caught by catch (__ts_catchable)
class __ts_AssertionError extends Error {}
function assert(condition) { if (!condition) throw new __ts_AssertionError("assert: condition is false"); }

// throw x → throw __ts_throwable(x): only Error objects can be thrown
// catch (e) { … } → catch (e) { __ts_catchable(e); … }: rethrows TypeError, RangeError,
// ReferenceError, SyntaxError and failed asserts, as the interpreter does not catch them

// System.currentTimeMillis() → Date.now()
var System = {}; System.currentTimeMillis = Date.now;

// print() polyfill for environments without it (Node.js has console.log, not print)
if (typeof print !== "function") { print = function(s) { console.log(s); }; }

// __ts_add: handles Tinyscript's array+ semantics
// The + operator in Tinyscript allows array+array and array+element concatenation
function __ts_add(obj1, obj2) { ... }
```

**Every `+` expression in generated code is wrapped as `__ts_add(left, right)`**
to preserve Tinyscript's array concatenation semantics.

### `for` Loop Transpilation

- **`for (const x : items)`:** emits a loop over `__ts_iterate(items)` (the only
  `for` loop; the Lua-style numeric loop was removed in 0.23.0): arrays item by
  item (seeing items the body appends), the characters of a string, a copy of
  the entries of a `Map` or `Set`, a range lazily; the loop variable is a
  block-scoped `let` / `const` per iteration

### Identifier Shadowing

`getName(Identifier id)` calls `TinyscriptModelUtil.isShadowing(id)` to detect
name collisions between scopes. Shadowed identifiers are emitted with a
fully-qualified name (scope path joined with `_`) to prevent JavaScript variable
collisions.

## 13. Modules

See `docs/language-reference.md` (section 13) for the language side.

- **Grammar:** `Tinyscript: (imports += ImportStatement)* global=Global`;
  `ImportStatement` has either a `namespace` (`import * as m`) or `names`
  (`import a, b`) and a `path`; `FunctionDeclaration` and `VariableStatement`
  have an `exported` flag.
- **Scoping:** the names of the imports are part of the top-level scope
  (`TinyscriptScopeProvider`); the global scope only contains shared resources
  (builtins, REPL session lines), so files never see each other's names.
- **Validation:** `export` only at top level; imported names unique and not
  redeclared; no assignment to imported names.
- **Interpreter:** `TinyscriptEngine.setModuleLoader(ModuleLoader)` enables
  imports (without a loader, e.g. in the webdemo, `import` is an error). Before
  running a script, `bindImports` resolves each import, loads the module (cached
  per URI, so each module runs once), and binds the names in the current
  context. A module is validated and run in its own `ExecutionContext` whose
  outer context is the global one (builtins). Its exported names are copied into
  a `ModuleExports` object that is frozen afterwards. A stack of modules being
  loaded (rooted at the main script) detects cycles.
- **Generator:** `TinyscriptGenerator.generate(script, includeBuiltins, loader)`
  collects the imported modules in dependency order and emits each as
  `var __ts_modN = (function () { …; return Object.freeze({ … }); })();`,
  followed by `var a = __ts_modN.a;` per named import. Resolving, loading (with
  validation) and the cycle error are shared with the interpreter (`Modules`).
- **Native modules:** `std:fs` and `std:io` are implemented in Java
  (`runtime/fs/FileSystemModule`, `runtime/io/IoModule`); their URIs are
  `std:fs` and `std:io` (`Modules.isNative`). The engine creates their exports
  instead of running a script, and refuses them when sandboxed; the generator
  emits a small wrapper around node's `fs` instead. `std:io` reads the engine's
  `StandardInput` (`defineStdIn`: a stream, by default `System.in`, read up to
  each line break only, so that engines one after the other can share it, or the
  REPL's line editor); `lines()` is a `LinesObject` that the `for` loop reads
  lazily, like a range. In node, `std:io` reads file descriptor 0 with
  `fs.readSync`, so scripts stay synchronous.
- **Standard library:** `StandardLibraryModuleLoader` resolves `std:name` to the
  classpath resource `/std/name.tys` (source: `de.mkbauer.tinyscript/src/std/`);
  `FileSystemModuleLoader` delegates `std:` imports to it, and the webdemo uses
  it alone (no file imports). This also works from the webdemo's nested Spring
  Boot jar.
- **Loading:** `FileSystemModuleLoader` resolves relative paths against the
  importing file and bare paths via the module path, appends `.tys` if missing,
  and identifies modules by their canonical path (`toRealPath`).

## 14. Deployment Modes

### REPL

**Entry point:** `de.mkbauer.tinyscript.repl/src/.../TinyscriptReplMain.java`

With files as arguments it runs them in order, each with a fresh engine (files
share names only via import / export), and stops at the first error; without
arguments it starts an interactive session. Exit codes: 0 success, 1 syntax or
runtime error, 2 wrong usage. `run(args)` returns the exit code and takes its
own `out` / `err` streams, so the command line is unit tested
(`TinyscriptReplMainTest`).

The interactive session uses JLine 3 for readline-style input; the history is
kept in `~/.tinyscript_history` (one statement per line). Ctrl-C while a
statement runs stops it: the signal handler calls
`TinyscriptEngine.interrupt()`, which sets a flag that the engine checks at each
statement, loop iteration and call and turns into a `TinyscriptInterruption`
(not catchable by the script, like a resource limit); at the prompt Ctrl-C
clears the input, Ctrl-D leaves. jline's own Ctrl-C handler interrupts the
reading thread, which sometimes ends the read with `EndOfFileException` instead
of `UserInterruptException`; a set interrupt flag tells the two apart. `std:io`
reads the session's lines through a second `LineReader` on the same terminal
(line editing, but no completion, highlighting or history), set with
`TinyscriptEngine.defineStdIn(StandardInput)`; Ctrl-C there is a
`TinyscriptInterruption`, Ctrl-D the end of the input (`null`). Files read
`System.in`. Editing (in the REPL module): `TinyscriptLineParser` tells jline
that an input with an unclosed bracket or block comment goes on (`EOFError`), so
a statement over several lines is one input, edited and recalled from the
history as a whole; inputs that are incomplete in other ways (`let x = 1 +`)
still continue via `parse`. `TinyscriptCompleter` completes the word at the
cursor: the global object's names (the session's and the builtins), keywords and
commands, and after a dot the properties of the object and its prototypes; it
only reads properties (no getters exist), so completing has no effects.
`TinyscriptHighlighter` colors keywords, literals, strings, numbers, comments
and commands like the web demo. As in a file, every statement ends with `;`:
incomplete statements continue on the next line (`...` prompt), but a statement
that only lacks its final `;` (`x * 2`) is reported right away (`parse` tries
the input with a `;` appended). Syntax and runtime errors look as for a file
(the message, the source line and a marker; for a runtime error inside a
function also the calls, with the inputs of the session called `REPL1`, `REPL2`,
… as in node). Only the value of an expression statement is shown (strings
quoted, `TSValue.toString()`), not the `undefined` of a declaration, a loop or a
call like `print(x);`. Commands start with `!` (a line that ends with `;` is a
statement, e.g. `!done;`): `!load file.tys` runs a file in the session (its
resource is shared like the input lines, so later inputs see its top-level
names; loading it again replaces the resource), `!names` lists the top-level
names of the inputs and loaded files that have been declared, with their values,
`!reset` starts a new engine and resource set, `!help`, `!quit` / `!bye`.
Sandboxing is **off** (scripts can import `std:fs` and `std:io`). Each input
line is evaluated in a persistent `ExecutionContext` so variable state
accumulates across lines; the line resources are marked with
`SharedGlobals.share`, so later lines also _see_ the earlier declarations.

The helper script `de.mkbauer.tinyscript.repl/tinyscript` follows symlinks (so
it can be linked into `~/bin`), uses `JAVA_HOME` or the `java` on the `PATH`,
checks for Java 25 and starts `target/tinyscript-repl.jar`.

## 15. Key Design Decisions

**Why an integer switch with a `ClassValue` for dispatch?** EMF classifier IDs
are compile-time constants, so the switch is a jump table. Getting the ID via
`eClass().getClassifierID()` costs a virtual call on every node; caching it per
implementation class made the interpreter 5–15 % faster (measured on Advent of
Code programs, 2026-11-20). A Java pattern switch over the node interfaces was
not faster. Dispatch is still the largest cost of the tree walk; faster designs
(variables in slots, compiling the tree to closures) were deliberately not
chosen, to keep the engine easy to understand (see `TODO.md`).

**Why exception-based control flow?** `TSReturnValue` as a thrown exception
cleanly unwinds arbitrarily nested recursive `execute()` calls without threading
a "return flag" through every handler. `break` / `continue` work the same way,
with preallocated exceptions without stack traces, so they are cheap.

**Why a sealed interface for `TSValue`?** `undefined` and `null` are enum
singletons, the primitives are records and objects are `TSObject`s. A `switch`
over a value is checked for exhaustiveness by the compiler, and the common
`undefined` / `null` checks are a single pointer comparison.

**Why `GlobalExecutionContext` uses a `TSObject` instead of a `HashMap`?** The
builtins are properties of one global object, as in ECMAScript, and the
top-level variables of a script or REPL session live next to them. Scripts
cannot reach the object itself (`this` is `undefined` outside functions).

**Why a `WeakHashMap` for object tracking?** The resource monitor needs to track
live object count and memory without preventing GC. A `WeakHashMap`
automatically removes entries when the tracked object is collected, and the
callback (`onExpunge`) decrements the tracked memory total in real time.

## 16. Test Architecture

### Two test modules

**`de.mkbauer.tinyscript.tests`** (OSGi, `eclipse-test-plugin` packaging)

Uses `tycho-surefire-plugin` to run JUnit 6 (Jupiter) tests inside a full OSGi
container (`providerHint=junit6`, see below). Requires the target platform.
Tests use `@ExtendWith(InjectionExtension.class)` and
`@InjectWith(TinyscriptInjectorProvider.class)` to get a properly wired Guice
injector with all Xtext services. Test resources (`.tys` files) live in
`resources/`.

The `pom.xml` sets `<providerHint>junit6</providerHint>` because
`org.eclipse.xtext.testing` still requires the `org.junit` 4 bundle. Without the
hint, Tycho auto-detects the JUnit 4 provider and finds no tests.
`<failIfNoTests>true</failIfNoTests>` makes that case fail the build instead of
passing silently.

This module is the right place for:

- Tests that cover grammar, validation, or scoping details
- Tests that verify cross-reference resolution and IDE-level features

**`de.mkbauer.tinyscript.standalone.tests`** (plain `jar`, standard Maven
Surefire)

No OSGi. Bootstrapped via
`TinyscriptStandaloneSetup.createInjectorAndDoEMFRegistration()`. Runs in < 5 s.
Uses `node` (via Apache Commons Exec) as a differential oracle for the
transpiler.

This module is the right place for:

- Interpreter correctness tests (one `assertEquals` per language feature)
- Transpiler differential tests (interpreter output vs node output)
- Integration tests for complete programs

### Two-level test design in `standalone.tests`

| Level             | Class                      | Assertion                                           | On failure                                                                    |
| ----------------- | -------------------------- | --------------------------------------------------- | ----------------------------------------------------------------------------- |
| 1a — interpreter  | `InterpreterReferenceTest` | `assertEquals(expected, interpreterOutput(tsCode))` | Exact wrong value; points to buggy `TinyscriptEngine` visitor                 |
| 1b — differential | `TranspilerTest`           | `assertSameOutput(tsCode)`                          | Source + generated JS + both stdouts shown; paste JS into `node` to reproduce |
| 2 — integration   | `TranspilerVerifyTest`     | `assertTranspilerCorrectFromFile(filename)`         | Generated JS + node stderr shown                                              |

Tests run alphabetically: `InterpreterReferenceTest` → `TranspilerTest` →
`TranspilerVerifyTest`. Whole programs (Advent of Code 2021, 2023 and 2024, the
OO examples and every web demo example) are compared between interpreter and
node as well.

### When to run each module

After any change to `TinyscriptEngine` or `TinyscriptGenerator`, run the
standalone tests first:

```bash
./mvnw test -pl de.mkbauer.tinyscript.standalone.tests
```

Then run the full OSGi test suite before merging:

```bash
./mvnw clean verify
```
